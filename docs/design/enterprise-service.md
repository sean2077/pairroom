# Enterprise Native service

Status: approved product direction; implementation in progress. Updated: 2026-10-13.

This record owns the durable enterprise-service design. It is not a setup guide or evidence that a deployable service exists. [PR #151](https://github.com/sean2077/pairroom/pull/151) is the earlier draft delivery reference; subsequent local candidate commits, dirty-source seals and test evidence do not imply that its remote head has been updated. Delivery claims must identify the actual reviewed revision and executed checks. The original source baseline for this record is `7acbd2d67abd26d0742578d951eee8b7efb0b548`. Read [Architecture](../ARCHITECTURE.md), [Protocol](../PROTOCOL.md), [Storage](../STORAGE.md), [Security](../../SECURITY.md), and [Contributing](../../CONTRIBUTING.md) before implementation. Existing contracts remain authoritative for shipped behavior until explicitly changed with regression evidence.

## 1. Scope and decisions

Provide a single-organization, self-hosted Linux service for at least 100 registered users and 500 persisted Rooms as a capacity-planning workload, not a certified throughput claim. Native Agents continue running in user-owned harnesses on endpoints. Preserve Local-first and Embedded behavior. The first deployment has one active application instance. Prepare durable recovery and ownership boundaries now; implement planned handover and automatic failover in later milestones.

Enterprise mode uses generic OIDC, application-owned user/device credentials, explicit resource authorization, PostgreSQL persistence, and two symmetric remotely attachable slots. There is no requirement for a server-side checkout, vendor CLI, model credential, or local Agent. The administrator and Room Owner do not occupy a slot. Different endpoint sessions may use local and remote services concurrently, including two sessions on one device joining the same remote Room.

The approved first-phase scope is the predecessor closure of final regression R26, followed by delivery verification R27; private integration R28 is excluded, and HA R29/R30 remains later work. Logical Projects R13b are deferred only past the first vertical slice, while Projects, UI, attachments, deployment recovery and measured capacity remain mandatory first-phase work. Any revision to R26's dependency edges must explicitly describe the resulting scope change. Completing a vertical slice does not authorize publication, merge, push or external deployment.

Do not introduce a second Relay protocol/state machine, mandatory endpoint daemon, dynamic Go plugin system, general workflow engine, public SaaS tenancy, multi-Agent group chat, or distributed message broker. Enterprise infrastructure does not start arbitrary endpoint processes or execute vendor turns. Identity-provider implementation is external to this repository; public code, fixtures and CI use only standard protocols and synthetic identities.

SQL table names, HTTP routes, package boundaries and numeric defaults below are design candidates, not existing interfaces. The implementer may refine them with documented rationale while preserving approved behavior and security boundaries.

## 3. Resource model and authorization

Separate Organization, User, ExternalIdentity, DeviceRegistration, AgentInstance, Project, Room, RoomMembership, Slot and Binding. Each enterprise resource belongs to the configured organization. Use stable internal IDs and enforce foreign-key/uniqueness constraints; display names, email addresses, Runtime names and filesystem paths are not identities.

ExternalIdentity maps a configured trust connection and exact issuer/subject to a User. Do not auto-link accounts by matching email. Reconfiguring an issuer must not silently repoint existing identities. DeviceRegistration identifies an authorized installation/OS-user environment, not a hardware attestation. AgentInstance represents one native session on that device; Runtime is recorded on actual join and does not establish authorization. Binding contains Room, stable slot, AgentInstance and generation. Human publications must retain the human User ID in immutable provenance in addition to the existing protocol actor. A native session reservation is a service record: uniqueness is enforced by this deployment over its own DeviceRegistration and stable AgentInstance identities — deployment plus Device plus AgentInstance, or an endpoint-derived reservation key that does not reveal the raw vendor session — and holds across Rooms, including archived Rooms. The raw vendor session identity and the Runtime-plus-session exclusivity decision stay on the endpoint: the service never merges reservations across Devices because two records carry the same Runtime or session string, and Runtime never establishes authorization. Archiving retains the reservation, and only an explicit unbind, revoke or replacement retires it. The service does not arbitrate local Local/LAN bindings and does not claim cross-service vendor identity attestation; the endpoint's native identity record stays the authority for local exclusivity.

Room admission discloses full retained history, including messages predating admission, referenced attachments/images and same-Room quoted evidence. The Owner's member invitation states that admission grants the selected role immediately; there is no separate human recipient-accept state. The receiving Room page uses its current server-provided Owner/Member/Viewer role and clears that role disclosure on account or Room invalidation. The Binding approval page and foreground pending/accepted endpoint output state the same retained-history scope while keeping Owner approval and original endpoint completion separate. Device enrollment grants no Room history. These disclosures do not extend ACLs, expose unreferenced private drafts or vendor session transcripts, or change protocol bootstrap/receipt formats. Viewer cannot submit new messages, request a new Agent Binding or use Owner controls, but may still resolve an earlier accepted operation where the existing live read contract allows it.

Projects are logical, optional Room scopes. Project discovery and metadata must be filtered by explicit access; knowing an ID or sharing an organization is not authorization. Endpoint-local paths and vendor session identifiers are not public directory fields. Start with Room-level collaboration and avoid inventing implicit project-wide access through a single Room invitation.

| Operation | Organization administrator | Room Owner | Member | Viewer |
|---|---|---|---|---|
| Disable users/devices; set service policy | Yes | Own device only | Own device only | Own device only |
| Read Room/history/attachments | Only with explicit content access | Yes | Yes | Yes |
| Send as human | Only with corresponding Room role | Yes | Yes | No |
| Offer own Agent to a vacant slot | Corresponding Room role required | Yes | Yes, subject to admission | No |
| Invite/change members; retire a slot | Explicit Room authority required | Yes | No | No |
| Bind another user's Agent without their device authorization | No | No | No | No |
| Transfer ownership; archive Room | Explicit Room authority required | Yes | No | No |

Owner admission and endpoint consent are separate. A replacement is explicit, names the slot and observed generation, and never grants permission to impersonate its successor. Ownership transfer is transactional and targets an eligible active member. Keep historical authors when users are disabled or removed. Protect the last administrator; bootstrap through an explicit operator-selected identity, never an unauthenticated first-login race. Any emergency content-access mechanism must be explicit and audited; the ordinary administrator role does not automatically read all Rooms. A disabled Owner loses Room authorization immediately; ownership provenance, data and history remain. Members continue under their existing ACL without gaining new privileges, and no administrator gains content access from the disable. The Room enters explicit ownership-pending-recovery: privileged ownership operations stop until an authorized, audited transfer names an existing eligible Member. The user approved restricted governance recovery on 2026-10-13: an organization administrator with verified fresh reauthentication may explicitly transfer a disabled Owner's Room to an existing eligible active Member, with the ownership change and audit committed atomically. This permission grants no Room content access and cannot transfer a Room whose Owner is enabled. Re-enabling a user restores their untransferred Owner authority but never reclaims ownership transferred to someone else; previously revoked sessions, devices and grants remain revoked and require explicit new authorization. Implementation and acceptance of these approved policies remain tracked separately from this decision.

Default Room history visibility is full Room history for admitted members. Admission must disclose this. Reusing a Room for a different confidentiality boundary requires a new Room; filtering recent messages alone does not hide attachments, quotes or earlier context. A slot replacement does not revoke the previous owner's human membership: revoke that separately when needed. Application ACLs do not prevent a server operator from reading storage; transport security is not end-to-end encryption.

Governance recovery uses action-scoped evidence, not a persistent governance mode: a new browser-bound authorization-code transaction must verify signed authentication time and resolve the exact issuer/subject back to the acting administrator. The administrator supplies an original private recovery reason: valid UTF-8, 1–1024 bytes, at least one non-White_Space character, and no control characters except LF, CR and TAB. A live Owner may optionally supply a valid reason on ordinary ownership transfer; it is only a private audit note and introduces no reauthentication requirement. The exact text is preserved without trimming; it is absent from public Room facts, ordinary member views and operational metrics. Its short-lived one-use proof is bound to the action, Room, target member, expected Owner/revision and this reason and is consumed in the same transaction as the transfer and audit. The administrator needs no Room membership and receives no Room content; the operation must not load a content snapshot. A missing Owner membership alone does not authorize governance over an enabled Owner. After a transfer, stale requests and consumed proofs fail; any later governance operation requires a newly disabled current Owner and fresh evidence. Historical control events may describe accepted changes but never reconstruct current ACLs or credentials.

## 4. Generic OIDC boundary

Use Authorization Code with S256 PKCE and a server-managed login transaction. Bind random one-time state and nonce to the initiating browser, configured issuer/client, callback and allowed return path. A valid state received from another browser must fail. Bound concurrent login transactions, expiry, body sizes, outbound requests and timeouts; do not hold database locks across provider calls.

Use a maintained verifier and implement the checks required by [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html): trusted signature/algorithm, exact issuer, audience/authorized-party rules, expiry, nonce and requested authentication-time evidence. Match UserInfo subject when UserInfo is used. Do not accept arbitrary token-provided key URLs or dynamic issuers. Token/JWKS/discovery destinations and redirects are governed by operator configuration, including deliberate access to an internal IdP. Do not blanket-reject private networks that an internal deployment requires, and do not permit an end user to select arbitrary outbound targets.

Commit user/session creation before issuing a browser session. Cookies are Secure, HttpOnly and scoped appropriately; state-changing routes require CSRF protection and Origin checks. Sanitize return paths; keep tokens out of URLs, logs, browser storage and Agent context. Upstream credentials are not Pairroom API credentials. Local logout, provider logout and account disable are distinct operations. Reauthentication requires actual evidence, not merely another redirect. See [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html).

A successful login is also subject to configured admission policy. Arbitrary claims must not assign administrative privileges. Provider outage prevents new authentication; previously established Pairroom sessions follow their own expiry/revocation policy rather than silently gaining access or automatically being revoked without a defined reason.

## 5. CLI, device and Agent grants

Separate browser session, device/CLI authorization, and narrow Room Binding grant. Pin them to a stable service deployment ID plus trusted HTTPS origin, User, Device and scope; distinguish deployment identity, application instance identity, ownership epoch and restore/revocation epoch. Never forward an existing credential to a service from an invitation URL or HTTP redirect. Revocable opaque random tokens stored as hashes are a valid first implementation. Bearer tokens are not device-bound cryptographic proof; do not claim hardware or process attestation.

The normal CLI flow opens the system browser and completes a one-time, browser-approved Pairroom device enrollment. Bind completion to the requesting client secret or proof and display the destination service/device clearly. A loopback callback carries only a one-use completion code; validate exact loopback destination and transaction state. Keep upstream provider callback handling server-side. Follow [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html) for native authorization considerations. No client secret compiled into a distributed CLI is confidential.

Support a headless pairing flow only with an explicit verification step, attempt limits, polling interval, expiry and request binding. Reuse an IdP's supported device flow when applicable; if Pairroom implements its own enrollment, it owns that security boundary and must not assert RFC compliance without implementing the relevant contract. [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html) is the reference. Token rotation must address concurrent processes and a lost refresh response; never issue unlimited reusable previous-token grace.

Keep local files owner-only and use platform credential facilities where available. A session must select one binding unambiguously; changing cwd or the user's default server must not retarget it. Hooks remain inert when unbound, and noninteractive when login expires. They preserve uncertain work locally and surface a foreground recovery instruction. Same-OS-user Agents are not isolated sandboxes.

## 6. Revocation and race semantics

Every read, write, download, event stream, CLI operation and retained LAN-style entrypoint must resolve the same authorization policy. Authentication precedes idempotent receipt disclosure; a revoked credential cannot recover a receipt. An otherwise authorized retry can recover its accepted original receipt before a peer-generation check, preserving current Native semantics.

User disable, device revoke and membership removal durably change authorization state and audit facts. New operations authorized after that commit fail. Previously serialized operations may have completed before revocation; record that ordering honestly. Cancel active streams and recheck downloads at bounded chunk/time boundaries. Bytes already delivered cannot be recalled. Set and test a bounded stream-revocation delay; five seconds is a proposed lab target, not an implemented guarantee.

For revocation/write races, define a global lock order. Shared authorization-row locks or a proven transactional equivalent permit concurrent authorized work while conflicting with disable/removal. A version checked outside the transaction is insufficient. Document transaction isolation, locking and retry behavior. Do not use a lock mode that fails to conflict with a non-key status update. See [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html). Never hold the transaction open while waiting for Agent output, HTTP streaming or model execution.

## 7. PostgreSQL and Relay integration

Keep one transition implementation for Local and Enterprise. Refactor the current concrete JSONL dependency into the smallest event/command persistence boundary needed for transactional enterprise authorization. Merely replacing Append with an SQL INSERT does not solve stale in-memory state or cross-object races.

Suggested data domains are identity/membership, sessions/device grants, logical catalog/Room ACLs, Agent bindings, Room events and derived delivery/index state, object manifests, audit and service ownership. Separate authoritative control tables from rebuildable Relay projections; event replay must not recreate revoked authorization from old audit history. Event rows retain schema version, Room sequence, original actor/provenance and accepted operation identity. Commit authoritative control changes and corresponding audit/domain facts together.

An enterprise command transaction must:

1. Acquire the appropriate ownership, authorization and Room consistency guards in documented order.
2. Check live user/device/membership/scope before disclosing any stored result.
3. Recover an authorized existing idempotent result first; for a new operation, then validate current state and the expected binding/peer generation and prepare events.
4. Append contiguous Room sequence entries and update required control/projection/receipt records and the corresponding audit facts atomically.
5. Commit before publishing a notification, returning a successful write or delivering an envelope; apply or reload the in-memory projection only after the outcome is known.

If commit outcome is uncertain, invalidate the resident projection and reconcile by the original command identity. Do not retry external effects or publish guessed success. Sequence gaps, conflicting idempotency payloads and unsupported event versions fail closed. The exact order of generation checks versus accepted-receipt recovery must preserve the distinction between a new stale publication and recovery of an already accepted one.

Idempotency identity includes service, Room, publisher/binding generation and operation ID. Compare payloads including destination generation, attachments, quotes and review data. Do not deduplicate semantically different human commands. Claim-before-stdout, ack-after-stdout, unknown outcomes and no automatic replay remain unchanged. `handed_off` never means native model acceptance or exactly-once execution. Peer replacement keeps immutable history, retires old grants and leaves late output addressed to its original generation.

Use indexed pagination and bounded Room caches. Idle eviction cannot lose pending receipts, grants, leases or claims. PostgreSQL connections must not be held per long poll. One enterprise HTTPS listener with multiplexed Room routing is preferred over one public listener per Room. Notifications are hints; durable sequences/receipts remain authoritative. Capacity must include log replay, long histories and reconnect storms, not only fast empty-Room requests.

A closed PostgreSQL work connection may be replaced once on entry to a new explicit command under the serialized Store gate and existing operation budget. The replacement verifies the configured schema and deployment; the command still checks the original lease backend, start identity and epoch, live ACL and original operation receipt. It does not acquire ownership, clear a retired incarnation or fatal Engine, or retry any failed or uncertain effect. Failed replacement leaves the dead connection and durable facts unchanged; a caller must explicitly issue any later command or original-ID recovery.

## 8. Attachments and recovery

Define an ObjectStore boundary and use local disk initially if necessary. Object keys are server-generated and authorization uses Room-scoped manifests; a content digest is not a capability. Define upload-reserved, uploaded/verified, referenced, abandoned and deletion-pending states. Verify content length/hash, enforce concurrent quotas atomically, prevent symlink/path traversal, and serve untrusted content with safe download headers. A revoked token or cross-Room digest must not access an object.

Keep object bytes immutable while referenced. Record logical deletion first, delete asynchronously after a retention grace, and make garbage collection retryable. Database and object storage have no implicit shared transaction. A consistent backup manifest and object-retention barrier must protect objects needed by the database restore point. Local disk attachments block cross-host handover until bytes are copied and validated; an interface alone does not implement HA.

Migration is explicit and copy-based. Do not reinterpret existing Local/LAN Rooms as belonging to the first OIDC user. Validate supported source versions and immutable actors/generations, assign enterprise ownership explicitly, create an isolated destination, and reauthorize endpoint bindings. Keep the source untouched. Do not revive local management tokens, LAN credentials or native automatic-reply contexts. Delay an import tool rather than ship an unsafe implicit migration. Any such tool is new and explicit: it must not revive the removed legacy import path or pre-binding history import, and it requires its own contract and documentation change.

## 9. Single instance now; ownership and HA later

Use stable deployment identity and persistent ownership generation. Initially reject a second active writer. A database-coordinated ownership record and a correctly scoped advisory lock are candidate primitives, not sufficient proof by themselves. Every mutating transaction must be fenced against the current owner, and a process losing ownership must stop serving private reads/deliveries as well as writes. Lock loss on one connection must not leave pooled connections writing as an old leader. Long-running transactions must be bounded.

The first release must recover after restart without requiring all users to log in again, except where revocation/restore policy demands it. Client reconnection has bounded exponential backoff with jitter, preserves operation IDs and resynchronizes durable cursors. Stream disconnects during a restart are expected and recoverable; do not advertise zero interruption.

HA-1 is a future planned drain/handover with compatible old/new readers and schema expansion before contraction. HA-2 adds unplanned failure takeover, database promotion, object availability and split-brain protection. Application fencing cannot protect two independently writable database primaries. PostgreSQL asynchronous replication may lose acknowledged commits on failure; synchronous policy trades latency/availability for stronger durability. Choose and test the required RPO/RTO before advertising HA. See [PostgreSQL standby documentation](https://www.postgresql.org/docs/current/warm-standby.html).

On restore, a backup may resurrect previously revoked tokens. Require an explicit restore fence/epoch rotation, then either reestablish revocation state from a trustworthy newer source or invalidate all restored sessions and grants. Keep history; do not reopen old credentials merely because their hashes exist in the backup. Secrets and object keys require separate protected backup/rotation procedures.

## 10. UI and operations

Provide My Rooms, Room details/members/slots, My Agents, My Devices/sessions, logical Projects and an authorized administration view. Differentiate online transport, active collector, idle, unknown delivery, retired binding, expired login and ownership pending recovery. No UI status claims the model is working or finished without evidence. Creation has no Runtime/provider/model picker for Native Rooms. Replacing a slot is separate from joining; show generation and consequences.

Scope cached drafts/outbox/read positions to deployment, User and Room. Account switching closes old streams and never submits another user's queued message. Tokens never enter localStorage. Human history shows stable author provenance, not the current slot occupant. Archived Rooms are paginated/read-only and do not stop user sessions. Browser and CLI use the same resource policy.

Linux delivery includes a non-root container/systemd option, example PostgreSQL/TLS configuration, exact proxy trust and canonical origin, persistent volumes, secret references, readiness/liveness, graceful drain and schema compatibility checks. Private endpoints/paths and credentials must not appear in examples, diagnostics or artifacts. A proxy's forwarded headers are trusted only from configured peers. No automatic embedded execution or local filesystem registration is exposed through the enterprise entrypoint.

Set user/device/active-Room/queue/request/upload/storage limits. Metrics use low-cardinality labels, exclude message content and identity tokens, and distinguish transport from model activity. Audit records identify internal principals, action, target, outcome and correlation ID with appropriate access/retention. Required audit persistence failure fails privileged mutation closed. IdP, database, disk-full and attachment failures each have explicit degraded behavior and operator guidance.

Capacity fixtures must cover 100 synthetic users and at least 500 persisted Rooms; exercise 50, 100 and 250 active Rooms plus an exploratory 500-active-Room scenario. These are test scenarios, not supported limits. Record hardware, message/attachment sizes, history lengths, churn, RTT, connection counts, p50/p95/p99, memory, storage growth, recovery time and correctness. Define the supported envelope from measurements rather than guessing a server size.

## 12. Remaining engineering decisions

Resolve in implementation ADRs without reopening the confirmed product direction: library/version/license selection; the supported PostgreSQL major; object-backup consistency; explicit import tooling boundary; measured capacity/default limits; and subsequent HA RPO/RTO. The Owner re-enable policy and restricted governance-recovery permission were approved on 2026-10-13 and are recorded in §3; subsequent HA still requires explicit RPO/RTO targets.

**Same-owner projection reload.** The current enterprise Handler and SQL Store do not retain a Room engine cache: authenticated reads and commands reconstruct bounded projections from durable SQL facts. A borrowed `RoomPort` never closes its deployment Store. Discarding and rebuilding a projection within the same ownership epoch performs no recovery, writes no facts and preserves live `delivering` claims and the original accepted operation receipts. `TestSameOwnerColdRoomProjectionReloadPreservesLiveClaimAndReceiptPG` exercises that boundary with repeated actual PostgreSQL reloads and a retained-heap measurement; the longer measured workload provides separate process-memory evidence. This implements the idle-unload requirement without inventing a resident-cache eviction scheduler. Deployment ownership recovery still conservatively reclassifies uncertain `delivering` claims to `unknown`; Local `Open` behavior is unchanged. A future resident cache must retain these same reload and recovery boundaries.

No current design choice authorizes removing existing approval gates, weakening dependency checks or changing published Native uncertainty semantics.

Decisions already taken in Stage A are recorded in §13; resolved items are removed from this list rather than kept as open questions.

## 13. Implementation decisions (Stage A, 2026-10-12)

Engineering decisions delegated by the plan's "engineering choices need an ADR, not a new product question" rule. Each remains refinable with documented rationale while the approved behavior and security boundaries stay unchanged.

- **Idempotency namespaces.** Two disjoint key spaces, never compared with each other. A Binding publication is keyed by deployment, Room, its exact Binding ID (slot and generation are carried inside that identity), the operation kind (`report` or explicit `send`) and that operation's own identifier — the report sequence for a publication, the client message ID for an explicit send. The current local engine already keys reports as bind ID plus generation plus sequence, and the enterprise key must not weaken that: two slots both at generation 1 with report sequence 1 are different operations with different owners. A human command is keyed by deployment, Room, human principal and its client command ID, and an explicit send that carries a human author keeps the Binding key with its author provenance rather than moving into the human space. Payload comparison for a repeated key covers destination generation, attachments, quotes and review evidence; a different payload under the same key is a definite conflict (the existing `send_payload_conflict` shape), never uncertainty. Neither path deduplicates by body.
- **Commit-unknown projection.** An uncertain commit invalidates the resident projection and reconciles by the original operation identity against durable state. No guessed success is published, no external effect is retried, and only statements that are safe as pure database work may be retried, with a bounded attempt count. This refines §7's step 5 without changing it.
- **Transaction isolation, lock modes and order.** Ordinary operations run at read-committed and take `FOR SHARE` on each authorization row they depend on (user, device registration, membership, Room role); disable, revoke, removal and role change take `FOR UPDATE` on the same rows, so they conflict with in-flight authorized work while authorized work stays concurrent with itself. Never rely on a lock mode that does not conflict with a non-key status update. Rows are acquired in one global order: (1) the ownership record, (2) authorization rows by kind — user, then device, then membership — and within a kind by ascending stable internal ID, (3) the Room consistency row, which also serializes sequence allocation, (4) the fact and audit append. Operations touching several users or devices lock every row of a kind in that stable order before moving to the next kind.
- **Ownership fence.** The ownership record holds the instance identity, the ownership epoch, and the exact lease backend identity (backend PID and its start identity). The owner connection holds a session advisory lock. A session advisory lock is released by the server when its connection ends, but the database never updates the application's ownership row, so an epoch comparison against that row alone proves nothing once the lease connection is gone.

  Every mutating transaction, and every private read or delivery path, therefore verifies the authority twice: it reads the ownership row `FOR SHARE` and compares instance and epoch, and it confirms that the registered lease backend itself currently holds the registered lock — matching `pg_locks` to `pg_stat_activity` on the recorded PID and start identity, the current database OID, the complete advisory tag (`classid`, `objid`, `objsubid`), `granted` and an exclusive mode. An application name is a diagnostic label, never the identity. Measuring this on PostgreSQL 17.11, the two-integer form registers `classid` and `objid` with `objsubid = 2`, while the single-64-bit form splits its key across `classid` (high 32 bits) and `objid` (low 32 bits) with `objsubid = 1`; both carry the current database OID, so the check must name the form.

  When the lease connection dies, the registered backend no longer exists, the check finds no holder, and the transaction is refused before it writes, reads privately or delivers. This depends on neither a time-to-live nor the instance observing its own lock loss.

- **Lease loss is sticky.** A lost lease retires that lease incarnation permanently: the instance stops being a writer, and the same instance and epoch never silently re-acquire authority, because that would let an old pool or an old capability pass again. Returning to service requires a new instance identity with an advanced epoch and a new registered lease backend (a restart or an explicit operator re-election), and the deposed incarnation's old authority stays dead even if a new backend later takes the same application name.
- **Takeover, in-flight transactions and verification points.** A takeover acquires the advisory lock (only possible once the previous holder's session has ended), then takes the ownership row `FOR UPDATE` and advances the epoch with a new instance and lease identity. Because every transaction holds that row `FOR SHARE` until it commits, the takeover waits for in-flight transactions and cannot interleave with one: a transaction that already passed its checks commits before the takeover completes, and no half-state is produced. Afterwards the deposed instance fails its next transaction on the epoch check even if a pool connection is still healthy.

  The holder check runs inside a transaction and is a point-in-time verification, not a lease that the transaction keeps alive. If the lease is lost after a transaction's check and before its commit, that transaction may still finish, serialized before the takeover. Therefore every new transaction, every subsequent private-stream chunk or reconnect boundary, and every envelope release re-verifies before serving; active private streams are cancelled on observed loss, and bytes already delivered are not recalled. Nothing here promises that an individual statement fails automatically or that served output can be retracted.
- **Transaction budget and retry classes.** PostgreSQL `lock_timeout` and `statement_timeout` are per-statement, so the whole-transaction wall clock is enforced by the application: each transaction runs under a context deadline and its connection is cancelled and rolled back on expiry, with `idle_in_transaction_session_timeout` bounding idle-in-transaction time. Only failure classes that prove no effect (`serialization_failure`, `deadlock_detected`, lock/statement timeout or context expiry before commit) may be retried, only when the whole unit is pure database work with a stable operation identity, with a bounded attempt count and jitter. Any outcome that cannot prove the absence of an effect is reported as unknown and reconciled by the original operation identity (§7). No transaction spans IdP calls, endpoint waits, model execution or streaming, and no lock is held across such work.

Stage A checked this primitive's shape on PostgreSQL 17.11 in a local test container (a design check, not an enterprise test): while the lease session lived, the holder check found it; after its backend was terminated with a confirmable wait and the lock was confirmed released, the check found no holder immediately and the tag fields above were read as stated. The same probe reproduced the refuted alternative — with the lease backend gone and no successor, an epoch-only comparison still passed and its write committed, while the holder check found nothing in that state. The check reads another session's visibility, so it protects against this service's own stale instances, not against a holder of the application's database credentials.
- **Human-principal provenance storage.** Enterprise rows carry the immutable human principal (User ID) alongside the protocol actor. Local Store 14 facts and the v7/v8/v9 envelopes keep their current shapes: this decision adds enterprise-only provenance and does not create a new Local format version, does not change matching or routing, and does not make a display label (`author`) an identity.
- **Session reservation release.** §3 owns the rule: the uniqueness unit is this deployment's own Device plus stable AgentInstance identity (or an endpoint-derived reservation key that reveals no raw vendor session), never a vendor session string the service does not hold and never a Runtime name. Its release is only an explicit unbind, revoke or replacement recorded as a durable fact, and the reservation stays visible to its owning user. An archived Room keeps its reservation rows; archiving is never a release, and a duplicate binding fails closed with a foreground recovery instruction.
- **Operator bootstrap.** The operator seeds the first administrator by an explicit, documented operator action on the service host (a one-time enrollment for a named identity), audited like any privileged change. There is no first-login race, no claim-derived administrator, and the last-administrator protection stays in force during bootstrap and recovery.
- **Enrollment and refresh lost-response recovery.** Refresh tokens are one-time-use and bound to their device registration. A rotation family records its immediate predecessor so a lost response can be recovered once, within a bounded window, by the same client with its own proof; after that the client must re-enroll explicitly. Concurrent processes serialize through the platform credential store, and no previous token is ever reusable without bound.
- **Dependency selection.** Generic maintained libraries are adopted for standard OIDC/JWT verification and PostgreSQL access, with the exact versions chosen at implementation time from current stable releases and reviewed through the allowlist, root/desktop lockfiles and notices in the same change. A downloaded proposal file is not an approval. A hand-written OIDC or JWT verifier or a hand-written PostgreSQL wire implementation remains prohibited; parsing and validating Pairroom's own application-issued opaque tokens is ordinary application code and is expected. The supported PostgreSQL major is an engineering choice recorded with the storage seam, not a product question. The first enterprise dependency change lands with the storage seam (§11 stage B), not before.
- **Storage boundary shape.** The seam carries the authoritative control and audit commits, contiguous Room event appends with their command identity, projection invalidation/reload, and an explicit unknown-commit result. Replacing an append with an insert is not the seam. Stage A pins the contract the second backend must reproduce as transition traces, using the existing Local fixtures as the retained baseline.

  The Local sub-slice has landed as a behavior-preserving extraction: `relay.Config.Store` is now the `Persistence` interface (`Append`, `Load`, `Close`) with the JSONL store as its local implementation, and a nil return alone means the fact is durably readable. A non-nil return asserts nothing about absence — the local writer closes itself on a write or sync failure and an uncertain tail may remain — so the engine keeps its original fail-closed behavior: no guessed success, no external effect retried on a guess, and reopening replays the durable truth. Adjudicating which fact an uncertain append committed, by that operation's immutable identity, payload and expected revision under a consistency guard, remains part of the transactional backend; a plain read that does not observe the fact cannot disprove a commit still in flight. This extraction implements no enterprise transaction semantics and does not claim any.

- **Storage driver selection.** The enterprise transactional kernel uses `github.com/jackc/pgx/v5` v5.11.0 — MIT, pure Go — with a minimized import surface: the core package and `pgconn` only, no pool. The reviewed allowlist increment covers four runtime modules (pgx, pgpassfile, pgservicefile, x/text) and eight further modules that are graph nodes only; the root and desktop modules resolve and review their graphs separately, and any increment beyond that reviewed set requires a new review.

- **Human-send v1, readonly snapshots and the Room host mode.** The human namespace carries an additive `human_send` operation: the kernel alone computes its versioned intent hash (the fact bytes are never hashed), validates the complete pinned message codec against the typed intent — kind `native.message.updated`, actor/from `user`, text-only UTF-8 body within the core limit, producer-contract fields pinned with unknown fields rejected — and replays the original stored fact for an identical intent. `ReadonlySnapshot` serves an authenticated, fence-held, lock-consistent view (the authoritative room row plus the complete contiguous event log, refusing with `state_invalid` on any encoding, index or contiguity disagreement); every refusal discloses no content and the read writes nothing. `rooms` gains the native `host_mode` column. This remains an internal port surface with no public entry, and the append_fact v1 contract is unchanged.

  The engine wiring has landed for the same narrow slice: an enterprise Room engine is constructed only from an authenticated read-only snapshot (never the reap-writing `Open`), executes one text-only human send per whole-command gate (plan, SQL and apply; queueing counts inside one budget), rejects every legacy mutator at its entry, and returns the canonical original result on a replay without moving the projection cursor. A lost commit outcome fails the engine closed and is explicitly not recoverable by read-only verification — restoring write capability is a separately reviewed step this slice does not implement.

- **Enterprise control model (S4-A1).** The SQL schema is now version 2 and is the only version this build accepts: a version 1 schema is refused before any state is opened, and a schema is never evolved in place once any persistent external deployment or a released version supports it (the Local format windows are independent and unchanged). One schema serves exactly one organization: the single-row `configured_org` anchor plus a named foreign key on every resource row makes a self-consistent resource graph for another organization impossible to insert at all, not merely inconsistent. Identities are exact — a trust connection with its immutable issuer plus the exact subject, no email in any uniqueness rule — and a mapping's key including its User is never relabeled or reclaimed in place. A device belongs to a User; a canonical agent is unique per (device, opaque stable source key), so a second random ID cannot be minted for one stable source, while two devices may carry the same opaque key; the Runtime kind is recorded at join and authorizes nothing, and no raw vendor session or endpoint path is stored. A Room's durable owner record is a User reference rather than a membership role: an owner-role membership must match it and both ends are checked at commit, an owner who loses the membership keeps the record, and identity rows are retained rather than deleted, with a tombstone implying `disabled` so the kernel's existing check stays fail-closed. Slots separate a stable head from immutable generations: a binding references the exact historical generation instead of the advancing head, one live binding per slot and one live reservation per agent across Rooms (archived ones included) are unique, Binding and slot-head rows cannot be deleted, so reservations can be released only by explicit retirement and a retired generation cannot be reused under a new Binding ID. A head starts at generation 1 and may only hold or advance by one. A retirement timestamp is write-once and requires a reason containing a non-whitespace character on both insert and update, using the Unicode White_Space definition rather than a visual-glyph rule. Every live binding's generation must equal its slot head — a deferred constraint that locks the head row and reads the committed state, so a legal single-transaction replacement commits while a concurrent head advance and live binding cannot both commit. Logical Projects are optional Room scopes and authorize nothing. Device or Agent retirement metadata alone does not cascade into Binding retirement in this schema slice. Future typed revocation commands must explicitly retire the affected Bindings and persist their audit facts in the same fenced transaction under their reviewed authorization scope; no such application command is implemented here, and an offline device is not a revoked device.

  The evidence for this model is database-layer only: raw SQL against real PostgreSQL proves each foreign key, uniqueness rule, immutability guard and deferred constraint by its exact SQLSTATE and constraint name, including two real concurrent writers. No application command path, entry point or authorization decision is implemented or claimed by it, the original application-level gate-1 cases remain unverified, and the Room creation fact — its kind, payload and apply path — is deliberately not invented by this slice. The two fixture seeds (the shared `sqltest` seed and the sqlstore package's own) cannot share code because of the package boundary; each asserts one identical canonical snapshot so either side drifting fails its own test.

- **Atomic Room creation (S4-A2).** The internal human namespace adds the typed `room_create` operation. The caller retains a stable Room ID, client operation ID and prepared intent before submitting: name and the complete versioned collaboration value are normalized once, then validated unchanged on every commit and resolution. Organization and initial Owner are obtained from the configured deployment and authenticated, admitted live User; the request cannot select another Owner, a server workspace, a Runtime or a Binding. An existing enabled User record is the internal admission boundary for this slice; arbitrary OIDC profiles are not admitted by it. Organization-wide disable policy, administrative bootstrap and public authentication remain separate unimplemented surfaces.

  Creation atomically writes the Room control row, its Owner membership, the two generation-one slot rows and heads, the sequence-one `room.created` fact, the original operation result and a `room.create/accepted` audit record. No intermediate Room is committed. The fact retains the established `RoomMeta` fields and a required version-one `enterprise` origin containing deployment, organization, native host mode, Native v9 protocol, initial Owner and two vacant generation-one slots. This build accepts only enterprise origin version 1, with the exact lowercase JSON field names and no unknown, duplicate or trailing fields; extending that payload requires an explicit new origin version and reviewed reader/writer compatibility, rather than adding optional fields to version 1. The collaboration version is validated independently against its supported frozen policies. These are durable birth facts; the current Owner and ACL remain the live control policy and are not reconstructed as renewed privileges. The enterprise constructor and rebuild require this unique first fact, validate its complete codec and trusted origin, and derive vacant slots from it without fabricating a Binding or accepting current Runtime defaults. Low-level SQL primitive fixtures may still have empty logs; they are not valid enterprise Room constructor inputs.

  Room creation and its read-only result verification take the ownership row `FOR UPDATE` as their first lock, once, before User, membership and Room guards. This excludes an earlier database transaction until it settles even while the new Room row is still absent; the Go command semaphore and a missing-row query alone do not prove absence. The same exact-holder fence, operation budget, dependency recheck, commit classification and bounded verification connection from the existing kernel remain in force. The cost is a bounded deployment-wide exclusive interval for creation or its verification. Existing append and Human Send operations retain shared ownership: their Commit takes the existing Room row `FOR UPDATE`, and Resolve waits on that row with `FOR SHARE` before checking the operation, so their absence proof already has a database guard.

  Current live authorization precedes result disclosure. The same original key and frozen intent recover the canonical creation; a different intent conflicts. `CommitRoomCreate` refuses an existing Room without a matching operation as the body-free, definite `room_taken`, and never adopts it through an upsert. `ResolveRoomCreate` instead answers whether the exact requested operation exists: a guarded absence is `not_committed` with no fact, sequence or revision, even when another operation already created that Room. A creator removed from membership cannot recover content through the old creation key. Interrupted verification remains `unknown`, and no effect is retried automatically. Real-proxy tests exercise both unknown commit outcomes through Store retirement and a fresh lease incarnation: an explicit same-key retry returns the accepted original creation or creates exactly one Room after proven absence; repeating it returns the same canonical result. Stored creation payloads are strictly validated again before recovery, and an audit or event failure rolls back all newly created rows. These internal APIs and tests do not close the application gate-1 milestones or implement a public creation route.

- **Controlled deployment rebuild for a caller-observed unknown outcome (S3c-R evidence).** The recovery path for a caller that observed an unknown commit outcome (`connection_exception` / `commit_uncertain`) is a controlled rebuild of the whole deployment, not a same-owner hot repair. The caller keeps the original typed request — Room, principal, client identity, target and the complete original text — outside the failed service process. The rebuild retires every old Room engine (settling in-flight commands on their gates), then closes the shared store, and a fresh store opens a new instance identity with an advanced epoch through the existing reviewed APIs (`sqlstore.Open`, `sqlstore.RoomPort`, `relay.OpenEnterprise`, which only borrows the store and reaps nothing); `relay.Open` (which reaps) and same-owner connection restoration are not used. Verification is read-only, by the original key and the same intent: a replayed operation returns its original canonical fact — original message identity and creation time — with no second effect, a proven absence permits only the caller's explicit same-key re-send, and an unknown, conflicting, revoked or lease-lost verification sends nothing and leaves the outcome unresolved. No old fatal or sticky lease-lost incarnation is cleared, no lease is silently re-acquired in the same epoch, and nothing is reaped or retried automatically.

  The evidence is process-level, not object-level: a real child process loses its commit response through a proxy in both directions (accepted-then-lost, and broken before `COMMIT`), reports the typed unknown with its class to the caller over the test IPC channel, and exits; a second real child process then performs the restart itself — open the deployment, verify the pending outcome read-only with the original identity, key and intent, build the Room engine from an authorized read-only snapshot, and only then execute the separately received explicit send — and the rebuild is confirmed by a distinct process, a new instance identity and the advanced epoch, with a second writer refused while the old instance still lives. The pending-outcome path is measured, not asserted: the replacement process issues zero commits before it certifies the outcome. Two distinct Rooms sharing one store are rebuilt as one unit: neither Room's stored bytes nor the complete authorization state (every membership with its role and disabled flag, every user's disabled flag) changes, and the new instance serves both. Production service orchestration, persistent login/session restoration across a restart, Bindings, collectors, attachments and HA remain unimplemented and are not claimed here; the tracking plan's application gate-1 and the items that depend on it (R14, R23 in `TRACKING.md`) are not closed by this evidence, and the same-owner cache-reload question (§12) stays a separate decision.
- **Room membership transactions (S4-A3).** The internal `room_membership` operation freezes target User, action (`admit`, `change_role` or `remove`) and member/viewer role. It uses the existing operation runner and human namespace, taking the ownership guard exclusively before actor/target User and membership rows in stable ID order and then the Room guard; a target membership takes its strongest required lock immediately. New changes require the live acting User to match both the durable Owner and its live Owner membership. The Owner cannot be removed or demoted through this API. The membership row, version-one `room.membership.changed` history, operation receipt and audit commit atomically with the Room sequence/revision. History is descriptive and never restores an ACL. Removal retains the membership row disabled. Until the complete Binding/grant retirement plan lands, removal of a member with an active Binding is explicitly refused as `unsupported_control_state`; this is an internal implementation boundary, not completed application revocation. Accepted receipt disclosure still requires current read access; guarded absence of the exact membership operation returns `not_committed` with no fact or cursor, and interrupted verification stays `unknown`.

- **OIDC verification foundation.** The standard verifier is `github.com/coreos/go-oidc/v3` v3.21.0, with `golang.org/x/oauth2` v0.37.0 and `github.com/go-jose/go-jose/v4` v4.1.5. This adds no hand-written signature verifier. The application additionally requires exact configured issuer, nonce, UserInfo subject agreement when used, and a matching `azp` whenever supplied or whenever there is more than one audience; the latter is PairRoom's strict client-binding policy. Provider requests use a finite-timeout HTTPS client with operator-approved origins, bounded response bodies/connections, no environment proxy or redirects, and an explicitly selected token authentication style to prevent automatic authorization-code exchange retries. JWKS fetch attempts use a bounded per-provider budget (initially two per minute), shared with signed UserInfo verification; cached valid keys remain usable when that budget is exhausted. Browser-bound state is consumed atomically before the one permitted exchange. A fresh-authentication result requires signed `auth_time` at or after that transaction's start, subject to the explicitly configured bounded clock skew. The package returns verified identity and frozen application intent; it does not admit Users, create application sessions or grant permissions. Its bounded memory transaction store is a short-lived login-flow implementation, not persistent application session storage. Synthetic HTTPS IdP evidence is separate from actual service or private-provider acceptance.

- **Enterprise Binding projection foundation.** Version-one `native.enterprise.binding.updated` stores an explicit Agent identity, actual Runtime, slot, Binding ID/generation, active state and `park_enabled`; retirement also records its time and reason. It contains no vendor session, transcript path, local credential hash or LAN key. Enterprise and Local/LAN fact codecs reject each other's binding authority. Both reach the same generation and inbox projection transition after their own identity checks; replacing or retiring a Binding derives queued cancellation and uncertain in-flight delivery exactly once. Runtime and Agent identity cannot change within a generation, retired identities cannot revive, and two active slots cannot reserve one Agent. `park_enabled` is replayed from the fact and grants no claim or wake authority. SQL Binding transactions, grants and public endpoint operations are separate subsequent implementation work; a replayed identity does not authorize a caller.

- **Persistent application identity and browser entrypoint.** Deployment-scoped control commands now use the same discovery, transaction, ownership fence, commit uncertainty and read-only resolution machinery as Room commands. Their closed receipts and audit records commit with authoritative identity/session changes; no synthetic Room is created to hold global control. The explicit operator configuration admits exact connection/issuer/subject tuples and reserves bootstrap for one named identity. Matching setup replay never revives disabled accounts, administrative roles or old sessions. Effective last-administrator protection includes an enabled User, an enabled administrator role and a nonretired, admitted login identity, including admission removal and concurrent changes. Admission changes govern subsequent login. Account disable and every administrator-role change revoke the target User's current browser sessions atomically; re-enabling a User restores no revoked credential. Current User status and session revocation/expiry/restore epoch are checked inside each public Room transaction as well as at HTTP authentication. Restarting the application advances ownership without invalidating otherwise live sessions.

  `pairroom enterprise init` and `pairroom enterprise serve` provide a separate configured entrypoint. The browser HTTP adapter accepts one canonical HTTPS origin, direct TLS or explicitly configured immediate TLS-proxy peers, deployment-scoped Secure/HttpOnly cookies, and same-origin CSRF-protected writes. It exposes typed Room creation/membership and authorized public Room projections; raw event payloads, delivery receipts and credential hashes are never browser responses. OIDC completion precedes SQL admission/session commit, and only a confirmed matching receipt issues a cookie. A transient discovery outage permits startup with existing persistent sessions; new login discovery is shared and rate-bounded, while authorization-code exchange is never retried. The minimal landing supports login, current session, opening a known Room and logout. Device enrollment, native grants, full management/UI, complete Binding revocation, governance transfer, attachments and release gates remain subsequent work. Until the composite retirement transaction exists, membership removal or demotion to Viewer with that User's active Binding in the same Room, and global User/administrator changes with affected active Bindings, fail explicitly without partial effects.

- **Control refusal recovery.** `last_administrator` refuses an operation that would remove the last effective login-capable administrator; repeating the request cannot make it valid, and another eligible administrator must first be explicitly established. `invalid_control_state` requires inspecting the current state and choosing a new explicit action. `unsupported_control_state` identifies an implementation boundary, not a successful partial action or an instruction to retry automatically. None authorizes replay of an uncertain external effect. Restore-epoch mutation remains an explicit restore-operation responsibility under the deployment fence and atomic audit; the existence of an epoch field or a test fixture update is not a production restore workflow.

## 14. Device, Binding and startup decisions (2026-10-13)

The earlier foundation entries describe their scoped implementation points. The current continuation connects persistent Device authority, narrow Binding credentials, composite revocation, shared Relay operations, restricted ownership governance, startup recovery and logical resource management. It adds verified private attachments, stable original human authors, full bounded history paging, typed offline backup/restore and bounded operational resources. It remains an unreleased candidate: scoped component and Linux rehearsal evidence does not replace final integrated regression, fixed-revision independent review or a measured concurrency envelope. Registered users, persisted Rooms and simultaneously active load are separate capacity dimensions.

Device enrollment is an explicit browser approval followed by completion using the original endpoint proof and a one-use numeric-loopback callback code. The endpoint persists its candidate credentials and operation identity before the effect. Access credentials last 15 minutes; a refresh family lasts at most 30 days. Rotation consumes the current refresh credential, and recovery uses only the immediate predecessor, the exact original proof and candidate, within a two-minute window, once. Local logout stops endpoint use but does not claim server revocation; My Devices provides an explicit server revoke. Hooks never initiate login or renewal. Retained uncertain operations remain private, bounded and isolated from a later login's Device identity.

Binding admission has three distinct actions: an eligible Device requests a slot, its current live Room Owner explicitly approves, and the original Device proves consent to complete. The frozen request contains deployment/organization, Room, slot, observed generation, replacement flag, Agent and actual Runtime, Binding ID, applicant User/Device/family, restore epoch, grant ID/token hash, proof hash, park policy, request identity and expiry. Completion rechecks every mutable authority: current applicant User and membership, original Device/family and restore epoch, live Agent on that Device, current Owner User and Owner membership, approved-by identity, request status/expiry/proof, actual slot head/occupancy and Agent reservation. No native session or workspace path goes to the service. Archived Rooms retain Agent reservation. Replacing a Binding requires explicit replacement and observed generation, retires its grants in the same transaction and preserves historical authors and accepted receipts.

An unconsumed approval must not regain authority after an intervening revocation and restoration. User/Device/Agent retirement, relevant Room membership revocation or demotion, ownership transfer, and Room archive invalidate affected `approved` requests in the same transaction. Requests that were never approved remain pending and require a new explicit decision from the then-current Owner. Completed Bindings continue according to their own live Member authority; disabling or transferring the Owner does not retire other Members' otherwise valid Bindings. Re-enabling an untransferred Owner restores their authority through a fresh session, never through revoked credentials. A transferred former Owner stays a Member. Current control rows decide authorization; event replay cannot restore it.

Permanent same-transaction invalidation is the current approval ABA defense. The completion predicates check present authority; they cannot independently detect Owner A-to-B-to-A, User disable-to-enable, membership removal-to-readmission or archive-to-restore after the visible authority has returned to its original shape. Independent forced-state probes demonstrated that directly changing an invalidated request back to approved bypasses this defense; this is evidence of the storage contract dependency, not an authorized recovery route. Every authority writer must include the appropriate approved Binding requests in its invalidation set. Global User/Device retirement additionally invalidates approved Device enrollments. Restore invalidates unconsumed requests and action proofs and rotates the credential epoch. These writes, their measured audit effects and their failure rollback must be covered together; a future authority path cannot rely on live predicates alone.

Binding lifecycle, governance, catalog mutations and composite revocation select an exclusive ownership guard before visiting authority rows; reads select a shared guard. The initial request and scope lookups discover identifiers without taking request locks. Live actor, applicant and Owner User rows are ordered by stable ID, followed by credential and membership dependencies. Revocation locks its sorted affected approval set before Room guards and compares the rediscovered dependency set under the fence. Binding completion uses the already exclusive deployment guard to exclude concurrent approval/revocation before it reads or updates a request. It does not acquire a request lock and then upgrade to an exclusive ownership guard. Any future relaxation of the exclusive guard must first introduce a common explicit request/credential/Agent/slot lock order across all writers and their readers; the current serialization cannot be silently removed as an optimization.

ACL-13 governance is a closed transfer action for a disabled Owner User, not for a missing Owner membership alone. It requires a current administrator, an existing active eligible Member target, expected Owner and Room revision, and an original private recovery reason with actual signed fresh OIDC authentication bound to the same original browser session and exact action. Prepare and transfer hash the full intent including the reason; finish derives the same intent from its immutable original action reference, never request-supplied text. Read/list disclose it only to the original live administrator session. Accepted replay restores the original result; changed-reason transfer or Resolve cannot reuse it. Finish receipts must also match the original immutable action intent and expiry instant, so recomputing a result digest cannot relabel the reason or target. This integrity comparison does not apply current consumption, expiry or Owner eligibility to an already accepted result. The reason is recorded in private SQL governance audit detail while preserving typed target, operation and invalidation fields. The five-minute action proof is one-use; consuming it, changing ownership, appending descriptive history, recording the result and writing audit commit atomically. The administrator receives only action metadata and gains no Room content membership. A normal live Owner may perform their own explicit transfer without this administrative recovery permission or a mandatory recovery reason. Transfer and User enable share the exclusive deployment guard and live Owner checks: enable committing first prevents administrative takeover; a transfer committing first is not reversed by re-enable. Unreleased version-two alpha schemas missing the required immutable governance reason column are refused without migration; backup bundles require the matching fixed column registry and cannot import the earlier reason-less shape.

Shared Relay planning remains the owner of send/report/claim/ack/retry/cancel/park transitions. SQL commits the entire ordered fact batch, original typed receipt, audit and Room revision atomically; a zero-fact acceptance still has a durable receipt. Report identity uses the original Binding report sequence. Live authorization precedes accepted-result recovery, which precedes checking current peer or revision for a new effect. Narrow Binding credentials cannot invoke human queue retry/cancel. Browser queue controls are explicit Owner actions with stable IDs and revision checks; uncertain results require read-only verification. Archive stops new send/claim/retry, while a still-authorized collector may settle its original delivery receipt.

Each new ownership epoch runs delivery recovery before opening the public listener. The startup barrier pages all Rooms, including archived Rooms, and records each Room atomically with its recovery facts and operator audit. It changes only in-flight `delivering` work to `unknown`, preserving the original receipt, peer generation and author; it sends no envelope and retries nothing. A corrupt Room or failed recovery refuses startup and seals that Store incarnation against later business mutation. A new process/epoch can continue after a partial startup. Once the epoch completion marker exists, repeated recovery is read-only and cannot reap claims created in that same epoch. Ordinary projection reload also remains read-only.

SQL's private event wrapper uses fact codec 2: `{codec_version:2, origin_kind, origin_user, event}`. `origin_kind=user` requires the real causally initiating internal User; `operator` requires null User and a system actor. The indexed provenance must exactly match the canonical encoded wrapper. Automatic startup recovery and lease expiry use operator provenance; a User-requested disable/transfer keeps its actual initiating User in its causal audit, without attributing it to the old approver. Old same-schema shapes without this explicit codec/provenance are refused before ownership changes. This private SQL encoding does not change Local Store, provisioning or checkpoint formats and is not an implicit migration.

Native private State 4 pins HTTPS origin, deployment, User, Device, Agent, server Room, Binding and generation. Existing State 2/3 remains readable on its original Local/LAN route; unknown future formats fail closed. A process restart or cwd change cannot retarget a session. The endpoint journals claim identity before its request, saves the returned receipt before stdout, and only acknowledges after stdout completes. Reconciliation verifies the original operation and never prints an uncertain old envelope. A saved successful-stdout/absent-ACK state permits only an explicit same-receipt ACK retry. Transport delivery is not model acceptance. Before a new claim request, an expired collector poll while waiting for the private Binding or native-identity lock is an empty wait, while the caller's own cancellation or deadline propagates. Identity mismatches remain authentication failures. Once a claim request has its durable journal, request failure remains uncertain and requires original-operation reconciliation; it is not converted to an empty wait.

Logical Projects have explicit memberships independent of Room content access. Project membership never grants Room history; a Room invitation never grants Project-wide discovery. Browser catalogs are paginated and filter by current authority. The UI separates the current authenticated account from its bounded recovery journal, keyed by origin, deployment, User and Room. Credential, CSRF and cookie values are never persisted in browser storage. Reload imports an unresolved intent for explicit verification, not automatic submission; switching account clears active content and cannot load or send another User's pending work. Cross-tab broadcasts carry only nonsecret identity markers and trigger a fresh authenticated session read before another view is displayed.


### Work connection admission (2026-10-14)

After a context cancellation closes the work connection, the next explicit command may create one bounded candidate connection under the serialized Store gate. Before adopting it, configure all server budgets, verify schema/deployment, hold the ownership row FOR SHARE and verify the original lease PID, backend-start identity, epoch and advisory-lock holder. Ordinary commands also require the durable restore barrier to be clear; typed offline restore/recovery commands retain their existing barrier rules. Reject and close the candidate on any failed check, preserve sticky lease loss, and retain the original dead work connection. The normal effect transaction repeats its full fence and live authorization; connection admission never acquires ownership, clears Engine fatal state or retries uncertain effects. These admission checks must not be silently removed as a pooling optimization.
