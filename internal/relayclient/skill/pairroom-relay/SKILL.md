# PairRoom relay

Run through this native session's tools. An existing binding follows the session across directories and task worktrees; cwd is not the Room's identity. Use `--repo` to choose an initial workspace or resolve a reported ambiguity, not on every message. Reuse the Room for follow-up work and follow the bind result's collaboration rules. Do simple work directly and involve the peer only when useful.

**Create** (`/pairroom-relay [peer] <topic>`): if the first argument is `claude|cc|codex|grok`, pass `--peer-runtime` with that peer and use the remainder as the name; otherwise infer `--peer-runtime claude|codex|grok` only when the topic or current prompt clearly names exactly one peer distinct from this session; otherwise omit the flag. Run `pairroom relay bind --create --name "<topic>"` with `--peer-runtime` when resolved. The creator defaults to Agent 1 regardless of runtime; the peer joins Agent 2. Pass `--slot` only when explicitly requested. Only if preflight explicitly says no Room was created and `--peer-runtime` was not already passed, choose the intended peer and retry once with `--peer-runtime claude|codex|grok`. Otherwise follow recovery instructions, never repeat `--create`. Give the peer the returned `peer_join_local` for the same workspace, or `peer_join` with its explicit paths; do not reconstruct it.

**Join/resume**: `pairroom relay bind`. Follow candidates only when ambiguous; slots are `--slot 1|2`, not runtimes. Bind is immediately usable: no nonce, status check or extra finished turn is required. Do not re-enter session/provider settings. After joining a Room whose peer is already bound, announce it with one fire-and-forget `pairroom relay send` line (no wait, no peer handle): the peer learns the Room is complete, and the delivery exercises the full relay loop. A first binder's announcement only queues for the future peer and verifies nothing yet; skip the announcement when resuming an ongoing collaboration.

**Discuss**: receiver runs `pairroom relay wait`; sender runs `pairroom relay exchange --id <stable-id> --text "<message>"` (`--text-file <path>` for existing long text, `--text-file -` for stdin). Both wait up to one hour by default, renewing in the CLI without model turns. Reuse an ID only for the same publication. After a confirmed send times out, use `wait`, not another send. Finish with `send` without another wait or a final peer handle unless a second publication is intended. Use `status`/`reconcile` for uncertainty or failures, not after every confirmed publication. When a harness shows only an output preview, read its supplied full-output file before acting; stdout acknowledgement does not prove the complete input reached the model.

**Large evidence**: do not read an existing file into tool output just to retype it into `--text`. Keep short decisions inline; send deltas instead of repeating reports already sent. Use `send/exchange --ref <path>` with a short question for optional large evidence: only its absolute path, size and SHA-256 are sent, not uploaded content. Both sessions need access; retain the file, verify its hash and read needed sections. Changed evidence needs a new publication ID. For an expected large incoming reply, `wait/exchange --output-file <new-path>` saves the full envelope and prints a locator; read that envelope before acting. Its parent directory must exist and be writable; no existing file is overwritten; retry collection with a fresh path. Prefer inline output for small replies to avoid an extra read. File paths remain relative to the tool's actual cwd, not the binding workspace. These flags need the current CLI. For consequential reviews add `--review` and optional `--review-repo <task-checkout>` / `--review-base <ref>`; compare with `review --id <published-id> --review-repo <task-checkout>`. A version observation is neither an atomic snapshot nor approval. Inspect independently before exchanging arguments when useful; report evidence and unresolved decisions without forcing consensus.

**Stay reachable** at the harness's real cost. Where the harness wakes on tracked background completion and idle waiting burns no model turns, prefer staying reachable whenever bound: keep exactly one background `pairroom relay wait` for this bound session with a long timeout (0 waits until cancelled; finite maximum is 21600 s) so it returns on real input rather than expiring per short cycle — empty expiries may cost resolving turns; resolve its result before another collector; re-hang after any expiry while the binding is live, since a quiet Room is not by itself a reason to cancel; cancel at unbind or on explicit human instruction. In a poll-only harness, stay reachable only while a joint task is active; do not keep a background relay wait or repeatedly poll merely to stay reachable: a tool runner can surface those cycles as recurring model/tool turns, and a live collector can suppress automatic wake even when its stdout is never shown to the model. End the turn instead — the bounded Stop park and, in a wake-enabled Room, the automatic Service wake turn queued input into your next turn. When a reply is expected imminently mid-task, block in a single foreground `wait`/`exchange` within the current harness tool timeout (non-normative: where the tool runner yields at about 30 s, 20–25 s leaves stdout/ack margin); after an empty foreground timeout prefer ending the turn over repeated re-waits. The CLI's one-hour default is a transport budget, not a guarantee that one vendor tool call can stay pending that long. Never rebind merely because cwd changed. Automatic wake is rate-limited and fail-closed. Unattempted cooldown work is deferred by the Service; reserved effects are never automatically retried: a failed wake leaves input queued until the receiver's next turn or a human nudge. Stop parking is bounded, not deep-idle wake. Agents never run a printed vendor wake command.

For Grok, review `/hooks`, reload with `r` after installation, and leave folder trust to the user. Grok reuses a compatible harness's project hooks by default: do not add a second Grok hook file when such a PairRoom Stop hook already covers the project; `relay install` strips a leftover Grok PairRoom Stop hook in that case. A readiness hint means run `wait`; clipped replies require explicit complete text, never a truncated prefix or a resend of confirmed text. Grok shell mode (`!`) is not a tool-call subprocess and does not set `GROK_SESSION_ID`; completed `!` commands also skip the Stop hook. Run bind/send/wait/exchange only through the agent's terminal tool. If a human ran `!`, execute the same command yourself — do not ask them to retry `!` or paste the session id.

On Service failure, run `pairroom daemon status`; ask the user to start it, or run `pairroom daemon install` only with confirmation. Use `doctor` for capability/cooldown diagnosis, `history --id <published-id>` for one message, or `history --pending` with returned cursors for unresolved work. Inspection never requeues work or proves model acceptance. Use CLI recovery, not private state inspection. Never bypass approvals or run concurrent collectors. A deliberate session change requires explicit `bind --replace`.
